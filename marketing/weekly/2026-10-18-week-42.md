## Reddit Post — r/LocalLLaMA

**Title:** How I handle context window pressure in a local AI tutor — 2-layer compaction in 561 lines

**Body:**

OpenTutor is an open-source local-first AI tutor (FastAPI + Next.js + SQLite, runs against Ollama or any OpenAI-compatible endpoint, MIT licensed). I want to write about a piece of infrastructure that took longer to get right than I expected: what happens when a tutoring session gets long enough to fill the context window.

**The problem is quiet**

A student opens a course, works for 45 minutes, asks questions, gets feedback. Everything looks fine from the outside. Then they open it again the next morning and the tutor has no idea who they are or what they were working on. Not an error — just silent context truncation. The LLM never complains when you drop messages; it works with what it has.

The naive fix is to just drop old messages. This works until a student references something they discussed 20 minutes ago ("remember the Chain Rule example?") and the tutor has no recollection. So I built a 2-layer system.

**Layer 1: LLM summarization at 70% fill**

`apps/api/services/agent/compaction.py` (370 lines) tracks context window fill and triggers compaction at 70%. Old messages (everything except the 6 most recent) get summarized by the fast-path LLM client — the cheapest, smallest configured model, which only needs to produce a short structured summary. The summary format is fixed:

```
## Goals
- [What the student is trying to achieve]

## Progress
- [Key milestones reached, concepts understood]

## Decisions
- [Important choices made during the conversation]

## Next Steps
- [Planned follow-ups or open questions]

## Key Facts
- [Important factual details to remember]
```

This replaces the dropped messages in the context. The tutor still knows what happened — it just knows it in compressed form.

**Layer 2: Emergency trim at 90% fill**

If the LLM call for compaction fails (Ollama is slow, circuit open, etc.) or the compacted context somehow still fills up, the system falls back to hard-dropping oldest messages at 90% fill. Always keeps the 6 most recent. If even those 6 exceed budget, falls back to 2.

**Intent-specific token budgets**

`apps/api/services/agent/context_trimming.py` (191 lines) handles per-category budgets before the context guard runs:

| Intent | RAG budget | Memory budget | History budget |
|--------|-----------|--------------|----------------|
| learn  | 4,000     | 1,000        | 1,500          |
| review | 2,000     | 2,500        | 2,000          |
| quiz   | 3,500     | 1,000        | 1,000          |
| plan   | 2,000     | 2,000        | 2,500          |
| general| 2,000     | 1,500        | 3,000          |

The defaults without an intent are RAG=3000, memory=1500, history=2000. The logic: during a learning session, you need more source material (RAG). During review, you need more knowledge about the student's history (memory). During a quiz, you mostly need the source material and can afford to compress history aggressively.

**Incremental compaction**

After the first compaction, the summary exists. If the session continues long enough to need a second compaction, running the full summarization again loses the structure of the first summary — the Goals section drifts, Decisions get re-summarized from the already-compressed version. Instead, a second compaction passes both the existing summary and the new messages: "update this, don't restate what's already there." This keeps the structured sections coherent across multiple compressions in a single very long session.

**What I got wrong first**

My first version treated compaction as an afterthought — it ran on every message, not on a fill threshold. This meant the context was always compressed to a fixed size, which was both wasteful (short sessions don't need it) and incorrect (it was dropping messages before they needed dropping). The threshold-based system is better. I'm still not confident the 70%/90% numbers are right — they were chosen to feel conservative, not from any benchmark.

The full implementation is MIT licensed. The LLM layer is `apps/api/services/agent/compaction.py` and `apps/api/services/agent/context_trimming.py`. Works with any Ollama model for compaction — llama3.2:3b handles the summary prompts well at ~200-400ms.

GitHub: https://github.com/zijinz456/opentutor

For anyone building local LLM sessions that run longer than a few turns: what threshold do you use for compaction? Have you found LLM-summarized context to be reliable, or do you end up with important information silently dropped?

## Reddit Post — r/Anki

**Title:** The AI tutor I'm building remembers what you struggled with — here's the memory architecture

**Body:**

I've been building OpenTutor, an open-source AI tutor that uses FSRS for card scheduling (same algorithm as Anki's FSRS integration). I want to write about a design challenge that doesn't get discussed much in AI product write-ups: how do you make an AI tutor that reliably remembers a student across sessions?

**The problem Anki doesn't have**

Anki doesn't have a memory problem because its state is explicit: the review schedule, the ease factor, the stability — it's all in the database. The tutor agent is different. It builds up conversational context — "the student confused kinetic and potential energy," "they prefer step-by-step worked examples over abstract explanations," "they asked about the same concept twice, which means it didn't land the first time." This is useful information. But it lives in the conversation history, which has a size limit.

**Two kinds of memory**

I ended up separating memory into two tiers. Short-term memory lives in the conversation history: what we talked about in this session. Long-term memory lives in the database: what's persistently true about this student and their learning.

The hard part is the transition. When conversation history needs to be trimmed (because the context window is filling up), the system first scans the messages to be dropped for anything worth preserving long-term. That includes:

- Knowledge gaps or misconceptions the student revealed
- Learning preferences (do they respond well to examples? do they prefer short answers?)
- Topics they found hard or asked follow-up questions about
- Any explicit statements about how they learn

Only after extracting that does the trimming happen. In theory, this means the most important information about the student survives the compression. In practice, the extraction is LLM-based and misses things. I've seen sessions where a student clearly struggled with a concept, the conversation was trimmed before the next session, and the tutor treated it as new material. That's a failure.

**What FSRS contributes to memory**

The FSRS data (stability, retrievability, review history) is a different kind of memory — it's precise, mathematical, and reliable. The spaced repetition layer never forgets that you rated a card "hard" twice in a row. The conversational layer can.

The knowledge graph (LOOM) is a third layer: concept nodes with FSRS-decayed mastery scores, edges for prerequisites and confusion relationships. This is more reliable than conversation history because it's updated explicitly from quiz results, not extracted from unstructured text.

**What I'm still uncertain about**

The right boundary between what belongs in the conversation, what belongs in the memory database, and what belongs in the knowledge graph isn't obvious. Right now it's a bit arbitrary: things that are hard to quantify go in the memory database, things that can be scored go in the knowledge graph, and transient context goes in the conversation. Whether students actually benefit from the memory layer in measurable ways — I don't have data on that yet.

OpenTutor is at github.com/zijinz456/opentutor. The memory architecture is spread across `apps/api/services/memory/`, `apps/api/services/agent/compaction.py`, and the LOOM knowledge graph in `apps/api/services/loom_graph.py`. MIT licensed.

Anki users: do you keep any external notes about *why* you keep getting specific cards wrong — misconception, not enough exposure, poor encoding on first review? How useful is that context when you come back to a card weeks later?

## IndieHackers Post

**Title:** I spent 561 lines on infrastructure nobody notices — and I think that's right

**Body:**

I've been building OpenTutor for about a year. Open-source, local-first AI tutor. FastAPI backend, Next.js frontend, SQLite, runs on Ollama or any OpenAI-compatible API. No subscription, no data leaving your device.

I want to write about a feature I shipped in March that I almost didn't ship at all, because it's invisible when it works.

**The problem I found too late**

I tested early sessions for a few minutes each. They worked fine. When I ran a longer session — 45 minutes, a student working through a dense topic — the tutor started losing track of things mentioned earlier. Not with an error, just quietly. The context window had filled up, old messages were getting truncated by the API call, and the LLM was working from an incomplete history.

This happens because a tutoring session has four things competing for context space: the conversation history, the source material (RAG docs), the student's long-term memory, and the system prompt. On a local model with a 32K context window — which is what many Ollama users have — a 45-minute session with moderate source material can fill it. On a 128K model it takes longer but it still happens.

**What I built**

`apps/api/services/agent/compaction.py` and `context_trimming.py` together are 561 lines. The system does two things:

First, it allocates the context budget by intent before anything else. A learning session gets more tokens for source material. A review session gets more tokens for the student's history. A quiz gets mostly source material. These aren't magic numbers — they're guesses based on what information matters for each mode. I'm not confident they're right.

Second, it watches context fill in real time. At 70%, old conversation messages get summarized by the cheapest available LLM (llama3.2:3b on most local setups, takes 200-400ms). The summary has a fixed structure — Goals, Progress, Decisions, Next Steps, Key Facts. At 90%, messages get dropped without a summary, keeping only the most recent 6.

There's also a step before trimming: scan the messages being dropped for anything worth keeping permanently — learning preferences, knowledge gaps, misconceptions. Write that to the memory database. This is where I'm least confident the system works. Extracting important information from free-form conversation is hard, and I know it misses things.

**The honest version of why this took 561 lines**

The first version was 80 lines and it just dropped old messages at a fixed history length. It was wrong in two ways: it didn't account for the size of individual messages (one detailed explanation could be 800 tokens; 20 back-and-forth quips could be 400), and it didn't distinguish between "this session just started and has nothing to compress" and "we're 40 minutes in and hitting context pressure." The token-counting, threshold-based, intent-aware version took more code.

I'm not sure the additional complexity was worth it. The difference between "silently drops messages at length N" and "intelligently compresses at 70% fill" is real but hard to measure without user testing at scale, which I haven't done. The system runs invisibly when it works, and failures in the extraction step — when important context silently doesn't make it to the memory layer — are even harder to notice.

**The pattern I keep finding**

The interesting infrastructure in OpenTutor isn't the AI calls themselves — it's the plumbing that controls what the AI sees. Context trimming, circuit breakers, state machines, knowledge graphs. These are what make the difference between a tutor that works for 5 minutes in a demo and one that works for 45 minutes in a real session. I keep spending more code on the plumbing than on the AI integration, and I think that's correct.

The codebase is at github.com/zijinz456/opentutor. MIT licensed. Pull requests welcome.

If you've built AI applications that need to survive long sessions: how do you handle context pressure? Do you compress, paginate, or just rely on large context windows and hope?
