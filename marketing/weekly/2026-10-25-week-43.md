## Reddit Post — r/LocalLLaMA

**Title:** I broke concurrent SQLite writes in a local-first AI app by using the wrong connection pool — here's what happened

**Body:**

I'm building OpenTutor, a local-first AI learning platform that runs entirely on your machine with your choice of LLM (Ollama, OpenAI, Anthropic, whatever). It uses FastAPI + Next.js + SQLite so there's no cloud account required and your data never leaves your device.

This week I found a concurrency bug that had been lurking since the project started, and it's embarrassingly subtle.

**The bug**

When running SQLAlchemy with SQLite, you have to pick a connection pool strategy. For in-memory databases (`:memory:`) you must use `StaticPool` — a single shared connection — because otherwise each pool slot gets its own isolated in-memory database and nothing persists between requests. So early in the project I added `StaticPool` for all SQLite connections.

That's correct for tests. It's wrong for production, where the database is a file.

With `StaticPool` on a file-backed database, all async requests share one connection. When FastAPI's async workers run concurrently, two requests can be inside the same SQLite transaction simultaneously. If request A's work rolls back — say, a validation error halfway through — it can roll back request B's already-committed writes too, because they're on the same connection.

The fix was 8 lines: detect whether the database URL points to `:memory:` and only use `StaticPool` in that case. File-backed databases get SQLAlchemy's default async queue pool, which gives each request an isolated connection.

**Why this took a while to find**

The bug didn't manifest under light load or sequential requests. It only surfaced when two users (or two browser tabs) hit write-heavy endpoints at the same time. In a local app that typically has one user, that's uncommon enough to escape casual testing.

I added 27 lines of WAL-mode tests that deliberately fire concurrent writes and assert that neither transaction's result corrupts the other. Should have written these at the start.

**What I'd do differently**

Start with a connection-pool integration test on day one. Connection behavior under concurrency is the kind of thing unit tests can't catch — you need two real requests running simultaneously against a real file.

For anyone else building local-first with SQLite + async Python: the StaticPool docs say it's for "test scenarios or single-threaded applications." I read "test scenarios" and stopped there. The "single-threaded" part matters a lot.

OpenTutor is MIT-licensed and on GitHub. Happy to answer questions about the local-first architecture or the LLM routing layer.

What are you running for local SQLite + async Python in production? Curious whether others hit this.

## Reddit Post — r/Anki

**Title:** My Anki-style app had a silent bug: custom workspace blocks were disappearing on reload

**Body:**

I'm building OpenTutor, an open-source alternative to Anki that uses FSRS 4.5 for scheduling and adds a block-based workspace you can arrange per subject. The idea is that your study environment adapts to what you're actually doing — if you're in heavy review mode, the flashcard and wrong-answer blocks expand; if you're planning ahead, the forecast and timeline blocks move forward.

This week I found a bug that had been silently eating workspace customizations.

**What happened**

OpenTutor's workspace has 12 composable blocks: notes, quiz, flashcards, progress, knowledge graph, review, chapter list, plan, wrong answers, forecast, agent insight, and summary. Users arrange them however they want, and the layout persists to localStorage so their setup survives page reloads.

The persistence layer validates each block type on save. If a block type isn't recognized, it's dropped rather than stored. This is intentional — it prevents corrupt data from old versions from persisting.

The validation used a hardcoded list of block type names. That list had 11 entries. Summary was the 12th block, added later. Nobody updated the list.

Result: any layout containing a summary block was saved without it. On reload, the summary block was gone. No error, no warning, no indication anything had been dropped.

**Why this matters for spaced repetition specifically**

The summary block shows a condensed view of what you've reviewed and what's coming due. It's meant to give you a quick orientation at the start of a session — the same "where am I?" check that makes Anki's stats page useful. Losing it silently mid-session means users reconfigure it, lose it again, reconfigure it again, and eventually assume the feature is broken.

Reliable persistence isn't glamorous. But for a study tool that people use daily, losing layout state is trust-eroding in the same way losing review history would be. Your workspace should be there when you come back.

**The fix**

Replaced the hardcoded list with a lookup against the map that already defines all valid block types and their default sizes. One source of truth instead of two. Added 70 lines of tests covering every block type, including an explicit test for summary.

The project is open source (MIT) if you want to look at the block architecture. I've been thinking about how to handle future block type deprecation — Anki has dealt with add-on compatibility for years and I'd be curious how others have approached versioned layout schemas.

What would you want to see in a block-based study workspace that Anki's current layout doesn't support?

## IndieHackers Post

**Title:** Two silent data-loss bugs, one root cause, and what I'm doing differently now

**Body:**

I've been building OpenTutor for most of this year — an open-source, local-first AI learning platform that runs on your machine with your own LLM. No accounts, no cloud dependency, your data stays local. This week's work was supposed to be CI cleanup. It turned into debugging two silent data-loss bugs that had been in the codebase for a while.

**Bug one: the block that kept disappearing**

OpenTutor uses a workspace of composable learning blocks — flashcards, quiz, knowledge graph, spaced repetition forecast, and so on. Users arrange them however they want and the layout persists between sessions.

One of those blocks, the summary view, was being silently dropped every time a user saved their workspace. The storage layer validated block types against a hardcoded list — 11 entries — and summary was block 12, added after the list was written. Nobody updated the list. Nothing threw an error. The block just quietly vanished.

I found it by noticing that one of my own test layouts kept losing its summary block. Spent about 90 minutes convinced I had a React state bug before I found the one-line mismatch in the storage validator.

The fix: two lines of code. Replace the hardcoded list with a lookup against the map that already defines all valid block types. Added 70 lines of tests to make sure I can never do this again.

**Bug two: the database that forgot concurrent writes**

This one was harder to rationalize away because the implications are worse. OpenTutor uses SQLite for local storage, and SQLAlchemy for async database access. Early in the project I configured SQLite to use `StaticPool` — a single shared connection — because in-memory SQLite (used in tests) requires it. File-backed SQLite doesn't. It needs separate connections per request, or concurrent writes can roll back each other's work.

I never made that distinction. Tests passed. Single-user local use passed. It only blew up under concurrent load, which in a "one person on their own machine" scenario takes a while to trigger naturally.

Fixed in 8 lines. Wrote 27 lines of concurrency tests. Added a comment explaining exactly why in-memory and file-backed need different pool strategies, so the next person (probably me, six months from now) doesn't revert it thinking it's wrong.

**What I'm taking from this**

Both bugs had the same shape: a correct decision in context A silently becoming wrong in context B, with no signal at the boundary. The hardcoded list was correct when there were 11 blocks. StaticPool was correct for in-memory databases. Neither blew up when the context changed — they just started producing wrong results quietly.

I've started adding what I'm calling "completeness tests" for anything that enumerates. If you have a list of valid values somewhere, you need a test that verifies the list matches the canonical definition of those values — not just that individual items work. 70 lines sounds like a lot for a 2-line fix. It's not.

OpenTutor is MIT-licensed and at about 8,000 lines now across the frontend and backend. I try to write one of these posts each week. If you're building something local-first or have dealt with silent enumeration drift in your own code, I'd like to hear how you handled it.

What's the quietest bug you've shipped that took the longest to notice?
