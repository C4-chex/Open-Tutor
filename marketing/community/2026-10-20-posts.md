## a) Hacker News — Show HN

**Title:** Show HN: OpenTutor – replaced "use Socratic method" prompt with a real FSM

**Body:**

Most AI tutors that claim Socratic questioning do one thing: prepend "use the Socratic method" to the system prompt. The problem is that instruction is ambiguous — the LLM interprets it differently each turn, forgets where the conversation left off, and often either gives the answer anyway or gets stuck in an annoying loop of open-ended questions when the student clearly needs a direct hint.

We built a proper finite state machine instead. Five states: PROBE, CLARIFY, CONFRONT, SCAFFOLD, CONFIRM. Twenty-five explicit transitions, driven by a classifier that reads the student's response and outputs one of five quality signals: correct / partial / wrong / confused / no_response. The engine is 287 lines in `apps/api/services/agent/socratic_engine.py`. The FSM runs per user+course, persisted in the agent KV store so state survives reconnections. Each state maps to a specific prompt directive — not a suggestion but a concrete instruction injected into the system prompt: "The student has a misconception. Present a counterexample. Do NOT say 'you're wrong'. Let the counterexample create cognitive conflict." The escape hatch: if SCAFFOLD runs for 4+ turns without improvement, the directive flips to a direct worked example. The FSM doesn't try to be clever indefinitely.

The initial state is picked from context, not randomized. Cognitive load > 0.7 → start in SCAFFOLD. Mastery < 0.3 → SCAFFOLD. Mastery > 0.7 → PROBE. Error type "conceptual" → CONFRONT. Error type "procedural" → SCAFFOLD. State initialization matters more than the transitions because the first message sets the tone for the whole exchange. The cognitive load score itself comes from seven behavioral signals: text fatigue cues, session length, unmastered error count, message brevity drop, help-seeking indicators, quiz accuracy, and answer hesitation timing (488 lines in `cognitive_load.py`). The score gets injected into the tutor prompt and also drives a parallel teaching-strategy extractor that logs what metaphors and examples worked for this specific student (356 lines, `teaching_strategies.py`). OpenTutor is self-hosted, runs on Ollama with `llama3.2:3b`, MIT licensed.

## b) r/LocalLLaMA

**Title:** I route model size hints based on cognitive load — here's how it works in practice

**Post:**

Sharing the adaptive model routing in OpenTutor (local-first AI tutor, Ollama default, MIT licensed) because I think the pattern generalizes.

**The setup:**

The router supports two model size hints: `"large"` and `"fast"`. In a typical local setup:

```bash
LLM_MODEL=llama3.1:8b       # "large" hint → tutor responses
LLM_MODEL_FAST=llama3.2:3b  # "fast" hint → classifiers, short tasks
```

Classification tasks (intent, response quality scoring, cognitive load NLP) always request `"fast"`. The main tutor turn requests `"large"` by default — but this changes dynamically.

**The cognitive load signal:**

The system computes a real-time cognitive load score (0.0–1.0) from seven behavioral signals: fatigue text cues, session length, unmastered error count, message brevity drop, help-seeking indicators, quiz accuracy, and answer hesitation timing. 488 lines in `apps/api/services/cognitive_load.py`. The score is derived from local DB queries + a regex pass on the user message — no extra LLM call.

**Where model routing changes:**

When cognitive load is high (score > 0.7), the Socratic engine (see `socratic_engine.py`) shifts into SCAFFOLD state: give one small hint, not a full explanation. SCAFFOLD turns request `"fast"` — the 3b model — because they're short, targeted, and latency matters more than depth when a student is already overloaded. Full explanations and CONFRONT-state responses that need nuanced counterexamples stay on `"large"`.

The net effect: under high cognitive load, the tutor gets cheaper AND more appropriate. You get faster responses exactly when a student is frustrated, and deeper responses when they're engaged and curious.

**Numbers on llama3.2:3b for classification:**
- Intent classification: ~280–400ms
- Response quality scoring (correct/partial/wrong/confused): ~300–500ms
- Cognitive load NLP affect pass: ~350–600ms

**Numbers on llama3.1:8b for tutor responses:**
- SCAFFOLD turn (short hint): ~2–4s
- Full explanation turn: ~5–9s
- CONFRONT counterexample: ~4–7s

If your use case is a long-running agentic loop on constrained hardware, the pattern "route model size based on task complexity signal, not just task type" is worth thinking about.

## c) r/Anki

**Title:** LECTOR: extending FSRS with concept prerequisites — what it adds and where it falls short

**Post:**

Hey, fellow Anki power user here. I've been building OpenTutor, a local-first AI tutor using FSRS-5/6 for flashcard scheduling. A few months ago I added LECTOR on top of it — a knowledge-graph-aware review prioritization layer based on [this arxiv paper](https://arxiv.org/abs/2508.03275). Figured I'd share what it actually changes in practice.

**What FSRS alone does (that SM-2 doesn't):**

FSRS schedules based on stability and retrievability — not a running ease multiplier. The forgetting curve is `R(t) = (1 + factor*t/S)^(-decay)`. Stability grows after each good review, shrinks after a lapse. The scheduler picks intervals that keep retrievability above a target (default 90%). This is strictly better than SM-2 because the stability model is per-card — a card you consistently get right accumulates long intervals regardless of early bad reviews, because difficulty is tracked separately.

**What LECTOR adds:**

FSRS treats every card as independent. LECTOR extends this with concept prerequisites. If you're reviewing "Integration by Parts" but you haven't consolidated "Basic Integrals" (its prerequisite), LECTOR de-prioritizes the dependent card and surfaces the prerequisite first, even if FSRS says the prerequisite isn't due yet.

The mechanism: LOOM builds a concept graph from your material. Each node has a mastery score. LECTOR clusters related concepts for co-review — studying similar concepts in a single session leverages interleaving without requiring you to manually tag anything. The cluster score is a weighted combination of: FSRS retrievability (how much you've forgotten), prerequisite deficit (how many unmastered prerequisites the concept has), and semantic similarity to recent session context.

**What it does well:**

On dense material with explicit prerequisites — calculus, pharmacology, grammar trees — LECTOR visibly shifts the review queue toward foundational cards when gaps appear. I tested this with a pharmacology deck: it consistently surfaced "mechanism of action" cards before "drug-drug interaction" cards when the mechanism mastery dropped below 0.6.

**Where it falls short:**

The concept graph extraction is only as good as the LLM that builds it. On PDFs with dense jargon, LOOM sometimes creates incorrect prerequisite edges. If "Krebs Cycle" and "ATP Synthesis" both depend on "Mitochondria" but not each other, a noisy extraction might link them as dependencies and create circular review pressure. The paper acknowledges this — LECTOR is designed for structured courses where prerequisite graphs are explicit or easily inferrable. It's experimental in OpenTutor for this reason.

**Compared to Anki:**

Anki doesn't have anything like this — it has no concept of prerequisites between cards, and interleaving is user-managed via tags and deck structure. LECTOR automates the interleaving decision. The tradeoff is you need a knowledge graph, which requires the LLM extraction pass on your material. For a 60-page PDF that takes 4 minutes to process, you get a graph automatically. For a deck you've manually built over years, you'd need to re-ingest the source material.

Implementation: 344 lines in `apps/api/services/lector.py`, backed by `loom_graph.py` (428 lines) and `loom_mastery.py` (361 lines).

## d) r/GetStudying / r/medicalschool

**Title:** I stopped re-reading slides and started asking "why" questions — here's what actually changed

**Post:**

Second year of med school. Gastrointestinal block. I had a bad habit that I think a lot of people share: I'd read through lecture slides and feel like I was learning because the information was familiar. Then I'd get to questions and blank out on mechanisms.

The problem wasn't the content — it was that I wasn't testing myself on the *connections*. I could recite "H. pylori disrupts the mucus layer" but if asked "why does omeprazole need to be combined with antibiotics rather than used alone?", I'd freeze because I'd never been pushed to link the mechanism to the treatment rationale.

I started using OpenTutor on my lecture slides. The AI doesn't just answer questions — it asks them back. When I'd say "omeprazole reduces acid" it would ask "but what does the acid protection failure actually mean for bacterial survival?", and keep narrowing until I'd built the connection myself. It felt annoying the first few sessions. Then I hit an NBME question about a patient on PPI monotherapy and I actually saw the reasoning chain in my head instead of guessing.

A few things that helped specifically:

**Don't ask "what is X". Ask "why" and "what happens if"**. The AI handles "what is" questions fine, but it handles mechanism questions better — it has the whole source material loaded and can build connections between your slides.

**Let it correct you without explanation first**. When I got something wrong, I started saying "tell me what I got wrong but don't explain it yet, ask me to reason it out." The tutor has a Socratic mode that does this automatically once it picks up the pattern — but you can also just request it.

**Use the knowledge graph view**. It shows which concepts you've mastered and which are prerequisites for things you haven't. I found I had a gap in "bile acid enterohepatic circulation" that was quietly blocking three other GI topics I thought I understood.

Not claiming this is magic — I still spend most of my time with First Aid and UWorld. But changing how I review with active questioning instead of passive reading made the passive reading stick better when I did it. The tool is free and runs locally — no subscription, your notes don't go anywhere.

## e) Dev.to / Hashnode — Technical Article

**Title:** How I built a Socratic questioning engine that actually changes behavior (not just prompts)

The obvious approach to "teach with Socratic questioning" in an LLM-based tutor is to put it in the system prompt. Add "use the Socratic method" and you're done. The problem is that instruction is too vague for consistent behavior. The LLM interprets it differently each turn. It doesn't track where the student is in the learning exchange. When the student is clearly stuck, it keeps asking open-ended questions instead of scaffolding. When the student is clearly ready, it still gives hints instead of probing with harder questions.

I wanted something that actually controls behavior differently per turn based on where the student is. That required moving the logic out of the prompt and into code.

### The architecture: a finite state machine injecting directives

The engine lives in `apps/api/services/agent/socratic_engine.py` (287 lines). Five states model the stages of a Socratic exchange:

```python
class SocraticState(str, Enum):
    PROBE = "probe"       # ask what the student thinks
    CLARIFY = "clarify"   # their answer was vague — narrow the question
    CONFRONT = "confront" # they have a misconception — present a counterexample
    SCAFFOLD = "scaffold" # they're stuck — give one small hint
    CONFIRM = "confirm"   # they got it — verify with a transfer question
```

Each state maps to a specific directive, not a vague suggestion. This is the SCAFFOLD directive, for example:

```python
_DIRECTIVES: dict[SocraticState, str] = {
    SocraticState.SCAFFOLD: (
        "The student needs help. Give ONE small hint that moves them forward "
        "without giving the full answer. Break the problem into a smaller step. "
        "Example: 'Let's start with just the first part. What is X?'"
    ),
    SocraticState.CONFRONT: (
        "The student has a misconception. Present a counterexample "
        "that challenges their current understanding. "
        "Do NOT say 'you're wrong'. Let the counterexample create cognitive conflict. "
        "Example: 'If that were true, what would happen in this case...?'"
    ),
    # ... (all five states)
}
```

At each turn, `get_prompt_directive()` returns a section that gets injected into the tutor's system prompt: `"\n## Teaching Strategy: SCAFFOLD\n<directive>"`. The LLM sees a concrete instruction per turn, not a style guide. The escape hatch: if SCAFFOLD runs for 4+ consecutive turns, the directive flips to a direct worked example — the FSM doesn't trap a frustrated student.

### Transitions driven by a classifier, not hardcoded

The state machine has 25 explicit transitions — five response quality signals × five states. The response quality classifier (a separate `"fast"` model call — ~300ms on llama3.2:3b) reads the student's message and outputs one of: `correct`, `partial`, `wrong`, `confused`, `no_response`. The transition table is a dict:

```python
_TRANSITIONS: dict[tuple[SocraticState, str], SocraticState] = {
    (SocraticState.PROBE, "correct"): SocraticState.CONFIRM,
    (SocraticState.PROBE, "partial"): SocraticState.CLARIFY,
    (SocraticState.PROBE, "wrong"):   SocraticState.CONFRONT,
    (SocraticState.PROBE, "confused"): SocraticState.SCAFFOLD,
    # ... 20 more
}

def transition(self, response_quality: str) -> SocraticState:
    new_state = _TRANSITIONS.get(
        (self.state, response_quality),
        SocraticState.SCAFFOLD,  # default: when uncertain, scaffold
    )
    if new_state == self.state:
        self.turns_in_state += 1
    else:
        self.turns_in_state = 0
        self.state = new_state
    return self.state
```

The `turns_in_state` counter is how the escape hatch works — SCAFFOLD for 4+ turns triggers the fallback to direct explanation.

### Initial state from context, not defaults

One thing that matters more than the transitions: where you start. The `_initial_state()` method picks the starting state from student context before the first turn:

```python
def _initial_state(self) -> SocraticState:
    if self.cognitive_load > 0.7:
        return SocraticState.SCAFFOLD
    if self.mastery < 0.3:
        return SocraticState.SCAFFOLD
    if self.mastery > 0.7:
        return SocraticState.PROBE
    if self.error_type == "conceptual":
        return SocraticState.CONFRONT
    if self.error_type in ("procedural", "computational"):
        return SocraticState.SCAFFOLD
    return SocraticState.CLARIFY
```

This uses three inputs: `mastery` (from the LOOM knowledge graph), `cognitive_load` (from the behavioral signal pipeline described below), and `error_type` (the last classification of the student's mistake, if any). Starting in PROBE when the student has low mastery is counterproductive — it wastes a turn asking for something they can't produce yet.

### The cognitive load input: seven behavioral signals

The `cognitive_load` input to the Socratic engine comes from `apps/api/services/cognitive_load.py` (488 lines). It computes a score from seven signals on each message:

```python
async def compute_cognitive_load(db, user_id, course_id,
                                  fatigue_score=0.0,
                                  session_messages=0,
                                  user_message="") -> dict:
    # Signal 1: text-based fatigue (from fatigue detector)
    load += fatigue_score * weight_fatigue

    # Signal 2: session length (performance degrades after ~45 min)
    session_fatigue = min(session_messages / norm, 1.0)
    load += session_fatigue * weight_session_length

    # Signal 3: unmastered error count (recent wrong answers not yet corrected)
    load += error_signal * weight_errors

    # Signal 4: message brevity drop (terse messages = frustration signal)
    brevity_signal = max(0.0, 1.0 - (msg_len / brevity_norm))
    load += brevity_signal * weight_brevity

    # Signal 5: help-seeking indicators (regex pass — "help", "stuck", "confused")
    load += help_signal * weight_help_seeking

    # Signal 6: quiz accuracy (low accuracy = high load signal)
    load += (1 - accuracy / target_accuracy) * weight_quiz_performance

    # Signal 7: answer hesitation timing (from practice response times)
    load += hesitation_signal * weight_hesitation
```

All weights are tunable in config. No extra LLM call — just DB queries and a regex pass. Runs in ~5ms.

### What this gains you

Before this implementation, the tutor would give the answer on the second attempt even if the prompt said "be Socratic." After: a student with low mastery starting in SCAFFOLD gets targeted hints until they break through, and the transition to CONFIRM only happens when the classifier sees a correct response. The escape hatch prevents the engine from frustrating students who genuinely need a direct explanation.

The pattern is reusable: any multi-turn agentic flow where you want the LLM to behave differently per stage of an interaction benefits from an FSM over a static system prompt. Move the "how to respond" logic into a state machine, serialize it to persistent storage, and inject a directive per turn. The LLM doesn't need to track state — the code does that.
