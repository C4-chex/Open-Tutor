## a) Hacker News — Show HN

**Title:** Show HN: OpenTutor – local-first adaptive tutor, FSRS upgraded to 5/6 (21 params)

**Body:**

We started with the FSRS 4.5 algorithm (17 parameters, the same one Anki ships) because the research was solid and the implementation was straightforward. The problem: FSRS 4.5 has a fixed forgetting curve where decay is baked in as a constant. You can tune stability, but the shape of the curve itself is immutable per card. For most learners that's fine. For anything with highly variable material — lecture notes mixed with dense formulas, for example — the fixed decay produced intervals that were too aggressive on hard cards and too conservative on easy ones once the session got long.

We upgraded to FSRS-5/6 (21 parameters). The main change: the forgetting curve decay `w[20]` is now a trainable parameter. `R(t) = (1 + factor * t / S)^(-decay)` — when `decay = 1.0` it's backward-compatible with FSRS-4.5, but it can be personalized. We also added same-day review handling: `S' = S * exp(w17 * (G - 3 + w18)) * S^(-w19)`, which prevents stability inflation from multiple intra-day reviews — something Anki doesn't do at all. And difficulty initialization switched from the FSRS-4.5 linear formula to exponential: `D0 = w4 - exp(w5 * (G-1)) + 1`, which makes the early-card difficulty estimates better calibrated. The implementation is 304 lines in `apps/api/services/spaced_repetition/fsrs.py`.

OpenTutor is a self-hosted adaptive learning workspace. 12 composable blocks (notes, quiz, flashcards, knowledge graph, study plan, analytics, more) that progressively unlock based on engagement. Upload a PDF, get structured content in ~30 seconds. Runs on Ollama (`llama3.2:3b` default), Docker-compose start. FSRS is one piece — the planner agent pulls forgetting cost estimates across your card deck to schedule review sessions without you having to open the flashcard view. Still public beta. MIT licensed.

## b) r/LocalLLaMA

**Title:** How OpenTutor handles provider fallback when your local Ollama is slow or down

**Post:**

Hey — sharing the provider fallback setup in OpenTutor (local-first AI tutor, Ollama default) because I think the pattern is worth talking about for anyone building multi-provider agents on local hardware.

**The problem:** Ollama can be flaky during heavy loads, especially on constrained RAM. If your local model is pegged at 100% trying to finish a previous request, the next request hangs for 10–30 seconds before erroring. For a learning session that feels bad enough that users just close the tab.

**The solution: circuit breaker + fallback chain**

The LLM router (`apps/api/services/llm/router.py`, 399 lines) maintains a `ProviderRegistry` with ordered fallback:

```python
# Progressive cooldown steps on failure
COOLDOWN_STEPS = [5, 10, 20, 60]  # seconds
CIRCUIT_OPEN_THRESHOLD = 3        # failures before circuit opens
CIRCUIT_RESET_TIMEOUT = 120       # seconds before auto-retry
```

When a provider fails, it goes into progressive cooldown — 5s, 10s, 20s, 60s on consecutive failures. After 3 failures the circuit opens and it's skipped entirely for 2 minutes, then auto-probed. Meanwhile all requests fall to the next healthy provider in the fallback order.

**Model size hints:**

```
LLM_PROVIDER=ollama
LLM_MODEL=llama3.1:8b          # "large" hint → main tutor responses
LLM_MODEL_FAST=llama3.2:3b     # "fast" hint → classifier, short tasks
```

The classifier and quiz evaluation code requests `"fast"`. The tutor agent requests `"large"`. The registry resolves these to whatever's configured under that variant, and if the variant is unhealthy it falls through to primary. So on a constrained machine (16GB M2), you can configure the 3b model as fast and the 8b as large, and the code doesn't change.

On llama3.2:3b for classification: ~300–500ms. On llama3.1:8b for tutor response: ~4–8s. Total per turn including FSRS retrieval and knowledge graph lookup: ~5–10s.

The circuit breaker also applies to cloud providers (OpenAI, Anthropic, Gemini via LiteLLM). So if you want Ollama as primary with OpenAI as fallback, it just works.

## c) r/Anki

**Title:** I upgraded FSRS 4.5 to FSRS-5/6 in my tutor app — here's what actually changed

**Post:**

Long-time Anki user here. I've been building OpenTutor, a local-first AI tutor, and I started with the same FSRS 4.5 algorithm Anki ships. After running it for a few months I upgraded to FSRS-5/6 (the newer reference implementation). Figured this community would appreciate the specifics.

**What FSRS 4.5 does that SM-2 doesn't:**

SM-2 schedules the next interval based on an ease factor multiplied by the previous interval. That means early reviews dominate: if you rate a card "hard" on day 1, you carry that forward into all future intervals via the multiplier. FSRS 4.5 models *stability* (days until recall drops to 90%) and *difficulty* separately. Stability grows after each successful review based on a formula that accounts for current difficulty, current stability, and retrievability at review time. The forgetting curve is `R(t) = 0.9^(t/S)` — exponential decay anchored at 90% target retention.

**What FSRS-5/6 adds over 4.5:**

1. **Trainable forgetting curve decay:** FSRS 4.5's decay is fixed. FSRS-5/6 adds `w[20]` as a parameter: `R(t) = (1 + factor*t/S)^(-decay)`. When `decay=1.0`, it's backward-compatible with 4.5. But per-user optimization can learn a different decay shape if the data supports it.

2. **Same-day review handling:** If you review a card twice in the same day, FSRS 4.5 would inflate stability (you got it right twice, so the algorithm thinks it's stronger). FSRS-5/6 has a separate formula for intra-day reviews: `S' = S * exp(w17 * (G - 3 + w18)) * S^(-w19)`. This prevents stability inflation from morning-then-evening review sessions.

3. **Exponential difficulty initialization:** FSRS 4.5 uses linear: `D0 = w4 - (G - 3) * w5`. FSRS-5/6 uses exponential: `D0 = w4 - exp(w5 * (G-1)) + 1`. The difference shows up on the first few reviews of hard cards — the exponential formula assigns higher initial difficulty more aggressively.

**How it's different from Anki specifically:**

Anki's FSRS integration (added in 23.10) uses FSRS 4.5. The same-day review issue is real — you can reproduce it by reviewing the same deck twice in one day and watching stability jump. OpenTutor's implementation is 304 lines with the 21-parameter model and same-day handling. The forgetting cost estimate (`estimate_forgetting_cost`) uses the FSRS retrievability formula to compute expected forgotten cards across your deck, which the planner agent uses to proactively suggest review sessions.

The 4.5 → 5/6 improvement is reported as 30%+ more accurate on benchmark datasets (reference: the fsrs-rs benchmarks). In practice for normal flashcard use it's subtle — the same-day review fix is the most noticeable change.

## d) r/GetStudying / r/medicalschool

**Title:** The thing that actually helped me stop re-reading the same chapter five times

**Post:**

I used to "study" by reading my notes. Then re-reading them the day before the test because I'd forgotten most of it. Then being surprised when I blanked on specifics during the exam. It wasn't a discipline problem — it was a feedback problem. I had no idea what I actually knew vs. what just felt familiar.

What changed for me: I started generating questions from my material before I felt ready, and tracking which ones I consistently got wrong.

The pattern:
- Read → immediately convert key points into questions (not summaries)
- Do those questions the same day, then a few days later, then a week later
- Stop re-reading anything you're getting consistently right
- Spend the time you saved on the specific things you keep missing

When I actually did this consistently, I stopped wasting time re-reading things I already knew and started spending that time on the 20% of material I kept forgetting.

If you want a tool that automates the question generation and spacing, I built one called OpenTutor (https://github.com/zijinz456/OpenTutor). You upload your lecture slides or a PDF, it generates quizzes and flashcards automatically, and the spaced repetition is handled by FSRS (the algorithm behind the most accurate flashcard scheduling research). It runs fully locally — no subscription, no data uploads, runs on your own machine. But honestly the method works even with index cards.

The key insight that took me too long to internalize: re-reading feels like studying because it's effortful and the material feels familiar afterward. Active recall feels harder *and* produces worse performance on the day — and dramatically better performance a week later.

## e) Dev.to / Hashnode — Technical Article

**Title:** How I built a multi-provider LLM fallback system for a local-first AI tutor

**Article:**

Building an AI application that runs locally creates a reliability problem nobody talks about in tutorials: your "API" is a local process that can be slow, out of memory, or flat-out unresponsive — and unlike a cloud API, there's no SLA and no retry-after header.

In OpenTutor, a self-hosted adaptive learning platform, every user interaction makes 1–3 LLM calls: a classifier call, a tutor response call, and sometimes a planning call. When Ollama hangs — usually because it's still finishing the previous request — the user sees a spinner forever. After too many of those, they close the tab.

Here's how we solved it.

### The circuit breaker pattern

The core is a `CircuitBreakerMixin` in `apps/api/services/llm/circuit_breaker.py`:

```python
COOLDOWN_STEPS = [5, 10, 20, 60]   # progressive cooldown in seconds
CIRCUIT_OPEN_THRESHOLD = 3          # failures before circuit opens
CIRCUIT_RESET_TIMEOUT = 120         # seconds before auto-reset

class CircuitBreakerMixin:
    def mark_unhealthy(self, error: str):
        self._healthy = False
        self._consecutive_failures += 1

        if self._consecutive_failures >= CIRCUIT_OPEN_THRESHOLD:
            self._circuit_open = True
            self._circuit_open_time = time.time()
            logger.error(f"Circuit OPEN for {self.provider_name} after "
                         f"{self._consecutive_failures} failures: {error}")
            return

        idx = min(self._consecutive_failures - 1, len(COOLDOWN_STEPS) - 1)
        cooldown = COOLDOWN_STEPS[idx]
        self._cooldown_until = time.time() + cooldown
```

Progressive cooldown means one flaky response doesn't immediately open the circuit — it just adds a short delay. After 3 consecutive failures, the circuit opens and the provider is skipped entirely for 2 minutes, then auto-probed.

### The provider registry

Every LLM provider is registered in a `ProviderRegistry` (399 lines in `router.py`). Providers have a name and an optional `primary` flag:

```python
registry.register("ollama", OllamaClient(), primary=True)
registry.register("openai", OpenAIClient())          # fallback

# Model-size hints: classify with fast, generate with large
registry.register_variant("fast", llama3_2_3b_client)
registry.register_variant("large", llama3_1_8b_client)
```

When a request comes in, `registry.get(name)` walks the fallback chain:

1. Check model variant hint (`"fast"`, `"large"`, `"small"`) → return if healthy
2. Try named provider if specified → return if healthy
3. Try primary → return if healthy
4. Walk fallback order → return first healthy
5. Raise `RuntimeError` if all providers are exhausted

```python
def get(self, name: str | None = None) -> LLMClient:
    # Model size hints first
    if name and name in self._model_variants:
        client = self._model_variants[name]
        if client.is_healthy:
            return client

    # Named provider, then primary, then fallback chain
    for candidate in self._candidates(name):
        if candidate.is_healthy:
            return candidate

    raise RuntimeError("All LLM providers are unhealthy.")
```

### Background health monitoring

A background task pings all providers every 30 seconds and caches the results. This means the health check in `is_healthy` is essentially free — it reads from the cache rather than probing live on every request:

```python
def start_health_monitor(self, interval: float = 30.0):
    async def _loop():
        while True:
            await self._refresh_probe_cache()
            await asyncio.sleep(interval)
    self._probe_task = asyncio.create_task(_loop())
```

### Model-size hints in application code

The application never references provider names directly. A classifier call requests `"fast"`, a tutor generation call requests `"large"`. This means you can reconfigure your model setup in `.env` without touching application code:

```
LLM_PROVIDER=ollama
LLM_MODEL=llama3.1:8b        # resolves to "large"
LLM_MODEL_FAST=llama3.2:3b   # resolves to "fast"
```

On a 16GB Apple M2, this gives ~300–500ms classification and ~4–8s tutor responses. The classifier is fast enough that users don't notice it.

### What we learned

The two patterns worth keeping regardless of stack: progressive cooldown (don't flip to fully unhealthy on the first timeout — start with a short delay) and model-size hints (decouple call sites from specific model names). Both made the system more resilient to the messy reality of local LLM runtimes.

The full implementation is MIT licensed in the OpenTutor repo: https://github.com/zijinz456/OpenTutor. The LLM layer lives in `apps/api/services/llm/` — 357 Python service files total, ~40,600 lines across the backend.
