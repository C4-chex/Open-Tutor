## b) r/LocalLLaMA

**Title:** How I eliminated blocking health checks from my local LLM router — background probe loop + circuit breaker

**Post:**

Built this into OpenTutor (local-first AI tutor, Ollama default, MIT). Sharing the pattern because it's generally useful if you run multiple local providers.

**The problem:**

Every time the router picked a provider, it did a synchronous health check — a quick `ping()` that added latency to every single request. When Ollama was healthy (99% of the time), you were paying a round-trip for nothing. When it was restarting, the health check just hung.

**What I replaced it with:**

A background probe loop that refreshes provider health every 30 seconds. On each request, `get()` just reads the cached health state — no blocking call.

```python
def start_health_monitor(self, interval: float = 30.0):
    async def _loop():
        while True:
            await self._refresh_probe_cache()
            await asyncio.sleep(interval)

    self._probe_task = asyncio.create_task(_loop())
```

Call once at startup. The probe cache holds the last-known health for every registered provider. `get()` reads it in microseconds.

**Circuit breaker layered on top:**

The circuit breaker (`circuit_breaker.py`, 83 lines) handles the failure case: progressive cooldowns of [5, 10, 20, 60] seconds on consecutive failures, circuit opens after 3 failures, auto-resets after 120 seconds. This is a mixin you mix into any `LLMClient` subclass — it's not specific to Ollama.

```python
COOLDOWN_STEPS = [5, 10, 20, 60]
CIRCUIT_OPEN_THRESHOLD = 3
CIRCUIT_RESET_TIMEOUT = 120

def mark_unhealthy(self, error: str):
    self._consecutive_failures += 1
    if self._consecutive_failures >= CIRCUIT_OPEN_THRESHOLD:
        self._circuit_open = True
        self._circuit_open_time = time.time()
        return
    idx = min(self._consecutive_failures - 1, len(COOLDOWN_STEPS) - 1)
    self._cooldown_until = time.time() + COOLDOWN_STEPS[idx]
```

**Three-tier routing on top of that:**

The complexity scorer classifies each request into fast/standard/frontier without an LLM call. On a typical Ollama setup:
- `fast` → `llama3.2:3b` (greetings, preference changes, classifiers)
- `standard` → `llama3.1:8b` (teaching, review, quizzes)
- `frontier` → falls back to standard if no frontier model is configured

**Numbers (M3 Pro, Ollama):**
- `llama3.2:3b` classifier call: ~280–450ms
- `llama3.1:8b` tutor response: ~4–9s depending on length
- Router overhead (complexity score + health cache read): <1ms

The fallback chain: if your primary is unhealthy, the registry walks the registered providers in order until it finds a healthy one. On a single-provider local setup (just Ollama), the circuit breaker prevents hammering a restarting Ollama and backs off gracefully.

## c) r/Anki

**Title:** We upgraded from FSRS-4.5 to FSRS-5/6 — here's what actually changed in the implementation

**Post:**

Hey, power user of Anki and FSRS here. I've been running FSRS in OpenTutor (local AI tutor, MIT licensed) and recently upgraded the scheduler from the 4.5 parameter set to the 5/6 set. Figured I'd write up what actually changed in the code for anyone else maintaining an FSRS implementation.

**The parameter count change: 17 → 21**

FSRS-4.5 uses 17 weight parameters. FSRS-5/6 uses 21. The additions are:

```python
DEFAULT_W = [
    0.4, 0.6, 2.4, 5.8,         # w0-w3: initial stability per rating
    4.93, 0.94, 0.86, 0.01,     # w4-w7: difficulty parameters
    1.49, 0.14, 0.94,           # w8-w10: stability parameters
    2.18, 0.05, 0.34, 1.26,     # w11-w14: retrievability parameters
    0.29, 2.61,                  # w15-w16: hard penalty / easy bonus
    0.0, 0.0, 0.0,              # w17-w19: same-day review parameters (FSRS-5)
    1.0,                         # w20: forgetting curve decay (1.0 = FSRS-4.5 compatible)
]
```

`w20` is the key addition: a trainable forgetting curve decay. In 4.5 the decay is hardcoded, which means the forgetting curve shape is fixed. In 5/6 you can fit it per user, which matters if your memory profile doesn't match the population average. With `w20 = 1.0` you get FSRS-4.5-compatible behavior — so the default is a clean upgrade path.

`w17-w19` handle same-day reviews separately from cross-day reviews. In 4.5, reviewing a card twice in one session uses the same stability formula as reviewing it a week later. In 5/6 there's a dedicated formula that avoids inflating stability from short-interval rereps.

**The forgetting curve:**

```
R(t) = (1 + factor * t / S) ^ (-decay)
```

`factor` is derived from the target retention rate (default 0.9), `S` is stability, `t` is elapsed days, `decay` is `w20`. In 4.5 this is equivalent to `decay = 1.0` always. In 5/6 it's a learned parameter.

**Practical difference vs Anki's FSRS:**

Anki's FSRS implementation is also FSRS-4.5 or 5 depending on version. The main practical difference with OpenTutor's implementation is the LECTOR layer on top: if a card's concept has unmastered prerequisites in the knowledge graph, LECTOR de-prioritizes the card in the queue even if FSRS says it's due. Pure FSRS treats every card as independent; LECTOR makes the queue topology-aware. This is experimental and can be disabled.

**Implementation:** 304 lines in `apps/api/services/spaced_repetition/fsrs.py`.

The paper claims 30%+ accuracy improvement over SM-2 (Anki's default), which matches what I've seen anecdotally on dense technical material where SM-2's ease multiplier can trap cards in permanent "hard" status after a few early failures.

## e) Dev.to / Hashnode — Technical Article

**Title:** How I built a complexity-based LLM router for my AI tutor (no extra model call needed)

The obvious approach to routing LLM requests is binary: simple tasks go to the fast small model, complex tasks go to the big one. The problem is that "simple" and "complex" are context-dependent in a tutoring system. A student asking "what is photosynthesis?" is simple if they're starting from scratch; the same question mid-session after 20 messages discussing Calvin cycles and electron transport chains is not — the model needs to synthesize and connect, not just define.

I wanted routing that understood request complexity without adding another LLM call to figure it out. Here's what I built.

### The scoring system

The complexity scorer lives in `apps/api/services/llm/complexity.py` (196 lines). It combines five signals into a single integer score, then maps that to one of three tiers: `fast`, `standard`, or `frontier`.

**Signal 1: Message length (0–150 points)**

A proxy for question depth. Short questions rarely need multi-step reasoning.

```python
def _score_message_length(message: str) -> int:
    length = len(message)
    if length < 20:
        return 0       # greetings, "ok", "thanks"
    if length < 80:
        return 30
    if length < 200:
        return 70
    if length < 500:
        return 100
    return 150         # long, detailed question
```

**Signal 2: Classified intent (0–300 points)**

Intent classification runs earlier in the pipeline (a fast model call) and its output is passed to the scorer. Different intents have radically different reasoning requirements:

```python
intent_scores = {
    "preference": 30,    # "change my study style"
    "general":    50,    # "what's on my study plan"
    "learn":     150,    # "explain osmosis"
    "quiz":      180,    # answer checking, feedback
    "assess":    200,    # diagnostic, knowledge gap analysis
    "plan":      250,    # multi-step curriculum generation
    "code":      250,    # code generation / debugging
}
```

**Signal 3: Complexity markers (0–100 points, capped)**

Regex pass over the message for high-reasoning phrases:

```python
_COMPLEXITY_PATTERNS = [
    (re.compile(r"\bprove\b",       re.IGNORECASE), 50),
    (re.compile(r"\bderive\b",      re.IGNORECASE), 40),
    (re.compile(r"\bstep[- ]by[- ]step\b", re.IGNORECASE), 40),
    (re.compile(r"\boptimize\b|\boptimise\b", re.IGNORECASE), 40),
    (re.compile(r"\bcompare\b",     re.IGNORECASE), 30),
    (re.compile(r"\bexplain\s+why\b", re.IGNORECASE), 25),
    # CJK equivalents also covered
]
```

**Signal 4: Conversation depth (0–80 points)**

Deep conversations have established context that the model needs to reason over:

```python
def _score_conversation_depth(history_length: int) -> int:
    if history_length <= 4:
        return 0
    extra = min(history_length - 4, 8)  # cap at 8 extra messages
    return extra * 10
```

**Signal 5: RAG context present (+50 if true)**

If the request will be answered with retrieved source material, the model needs to synthesize across documents — that's a harder task than answering from parametric knowledge.

**Tier resolution:**

```python
FAST_THRESHOLD     = 150   # score < 150 → fast
FRONTIER_THRESHOLD = 500   # score >= 500 → frontier
# 150 <= score < 500 → standard

def resolve_tier(agent_name, message, intent, scene,
                 history_length, has_rag_context) -> ModelTier:
    score = score_complexity(...)

    if score >= FRONTIER_THRESHOLD:
        scored_tier = ModelTier.FRONTIER
    elif score >= FAST_THRESHOLD:
        scored_tier = ModelTier.STANDARD
    else:
        scored_tier = ModelTier.FAST

    # Each agent has a minimum tier floor
    agent_min = AGENT_MIN_TIERS.get(agent_name, ModelTier.STANDARD)
    tier_order = {ModelTier.FAST: 0, ModelTier.STANDARD: 1, ModelTier.FRONTIER: 2}
    return scored_tier if tier_order[scored_tier] >= tier_order[agent_min] else agent_min
```

The agent minimum tier is important: a curriculum-planning agent should never route to `fast` even for a short message ("what should I study today?"), because the system prompt and response format for planning require a capable model.

### The provider registry

The router (`apps/api/services/llm/router.py`, 399 lines) implements the provider registry that `resolve_tier` feeds into. It's a multi-provider registry with automatic fallback:

```python
class ProviderRegistry:
    def get(self, name: str | None = None) -> LLMClient:
        # 1. Check model_variants (large/fast/standard hints)
        if name and name in self._model_variants:
            client = self._model_variants[name]
            if client.is_healthy:
                return client
        # 2. Try primary provider
        # 3. Walk fallback_order for any healthy provider
        ...
        raise RuntimeError("All LLM providers are unhealthy.")
```

Each `LLMClient` subclass mixes in `CircuitBreakerMixin` (`circuit_breaker.py`, 83 lines), which adds progressive cooldowns ([5, 10, 20, 60] seconds) and a circuit that opens after 3 consecutive failures, resetting automatically after 120 seconds. A background health monitor probes all providers every 30 seconds so `get()` reads cached health state instead of blocking on a live check.

### What you get in practice

On a typical local setup (`llama3.2:3b` as fast, `llama3.1:8b` as standard):

- A "change my notification settings" preference request scores ~60 → `fast` → 3b model in ~300ms
- A "explain why osmosis happens" question mid-session scores ~275 → `standard` → 8b model in ~4–6s
- A "derive the Henderson-Hasselbalch equation step by step" request scores ~540 → `frontier` → 8b (falls back from frontier if no frontier model configured)

The complexity scorer adds less than 1ms. No extra round-trip, no extra LLM call. The intent score is the only dependency on prior pipeline output, and it's already available from the intent classification that happens earlier in the message handler.

### When it falls short

The scoring is heuristic. "ok prove it" scores high on the `prove` marker and gets frontier-routed despite being two words. I added a message-length floor that prevents very short messages from scoring high on markers alone, but there are still edge cases. For a production system where model cost matters, you'd want to A/B test the thresholds against your actual query distribution. For a local-only deployment where the cost is just latency, the heuristics are good enough — routing a simple query to the slow model is the main thing to avoid, and length + intent catches most of those.
